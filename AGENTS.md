# AGENTS.md (proto — `TxnLab/zerosignal`)

Human reference: [`README.md`](./README.md) (repo map, build, releasing). Wire spec: [`SPEC.md`](./SPEC.md). TS SDK: [`sdk/README.md`](./sdk/README.md). Workspace-wide rules: [`../AGENTS.md`](../AGENTS.md), which a clone of this repo alone does not have — the rules that matter here are restated below.

## This repo is where payer behavior lives

This repo is the protocol **and** the payer SDK. The Go SDK is `go/zs` (with `zs/handler`, the OpenAI-compatible HTTP surface; `zs/tee`, the evidence verifier; `zs/tokenize`) and the TS SDK is `@txnlab/zerosignal` (`sdk/`), on top of the protocol packages (`go/{wire,ticket,selection,steering,transient,escrow,…}` ↔ `@txnlab/zs-proto`, `ts/`). `zs-proxy`, `tui -direct` and `cmd/zschat` run the Go SDK; the chat app (`client/`) runs the TS SDK. Discovery, routing, reserve, sealing, relay hops, streaming, receipt checks, settle / ack / protest, the reconciler, the refund watchdog, the ticket journal, wallet and MBR pool, and the routing stores (latency, relay reputation, backoff, exclusions) are all here.

**So a change to any of that is made here — never in a consumer.** The apps are hosts: they implement the SDK's ports (`sdk/src/ports.ts`, `config.ts`; `go/zs/config.go`, `journal.go`, `spend.go`, `registry.go`) and keep presentation, key custody, spending policy and storage. A consumer-side workaround for SDK behavior is a defect in waiting: the other consumer keeps the old behavior, and the next SDK bump silently changes what the workaround was compensating for. A change reaches a consumer only through a release and a pin bump (README "Releasing"; `../AGENTS.md` "The two publish gates").

**Discovery is the SDK's, and one seam sits outside it on purpose.**
- **Discovery.** The TS `Client` builds its own registry when `Config.registry` is absent, as Go's `New` does (`sdk/src/assemble.ts` ↔ `go/zs/assemble.go`): a `ChainOperatorSource` and a `DiscoveryRegistry` from the resolved `Config`, which it starts and stops in `close()`; a supplied registry is the caller's and is never stopped. It resolves the routing stores first and hands the same instances to the source and to dispatch, so the probes and the requests build one standing per relay; its default reputation store judges a relay's `relay_upstream_unreachable` claim by the source's `recallReachable`. One boot difference is deliberate: `Client.create` waits for the saved catalog and one chain read, and the first request waits for the first probe of every node, where Go's `New` waits for both. `client/` builds one `DiscoveryRegistry` per tab before login, tuned to a 60 s cycle and a probe budget of 64, and passes it to every `Client` as `Config.registry`. The SDK side is ported: `sdk/src/registry/` holds the chain read and probe pass (`ChainOperatorSource`), the refresh cycle (`DiscoveryRegistry`, Go's `DynamicRegistryProvider`: timer, lazy refresh, carry window, bounded probe set, transition logs) and the saved catalog in Go's v1 format (`persist.ts`), and `sdk/src/catalog/*` the derivation (the probe set, the ephemeral verdict, `buildUniqueModelRows`). New discovery logic belongs in `sdk/src/catalog` or `sdk/src/registry`, not in the client.
- **The client's per-node failover is deliberate.** The chat app's listener chooses each candidate and pins one SDK turn to it with `provider.only`, so the SDK's sideways candidate sweep sees a single node there. `zs-proxy` uses the SDK's sweep. Don't "fix" either toward the other.

## Source of truth

**When sources disagree: tests > code > [`SPEC.md`](./SPEC.md) > `AGENTS.md` > inline comments.** A disagreement is a **defect to report**, not a gap to guess across — say which two conflict and which you followed. A stale comment is indistinguishable from a live one, so a silent guess becomes the next change's false authority. `SPEC.md` can describe behavior not yet built; check the code before treating a SPEC sentence as shipped.

**Comments say WHY, never WHAT.** A comment restating the code below it can only ever become false. Explain the constraint, the rejected alternative, the failure a guard prevents. A load-bearing invariant belongs in a **test** — and in this repo, where most logic has a twin in the other language, in a **golden vector**, because a Go-only test protects only Go.

**Substantive changes get an independent review before they're reported done.** Spawn a fresh general-purpose subagent, tell it to run the `review` skill, and **name this directory explicitly** — the workspace root is not a git repo. Hand it the diff and this file, never the reasoning that produced the change. Act on the findings before reporting done.

**Then consider `mutation-adversary` — and ask the user first.** Most of this repo is in the classes where a green suite is not evidence: money / settlement / pricing, envelope crypto / AAD / canonical bytes, a security or provenance gate, an added guard or boundary comparison, a retry budget or state machine, and logic mirrored Go↔TS. Say what it would target and **wait for a yes**; hand it *only the diff*. Run rounds only while the survivor count falls, three at most.

## Request handling (Go SDK, `zs` + `zs/handler`)

- **Auth header**: always discard the caller's `Authorization`. The SDK injects no bearer auth — admission is the on-chain seal, not an upstream API key. `buildOperatorRequest` actively drops any `Authorization` sneaked in via the extras map.
- **Safety identifier**: the **node** sets `safety_identifier`, not the SDK. Only the node can ground the value in the verified-on-chain payer.
- **The escrow path is always on.** The wallet always opens a real `Payment + escrow.open` group; there is no stub or plaintext mode, and no `payment_mode` / stub-tx-provider / `zs.enabled` / `zs.accept_plaintext` knob. A reference to one is a leftover — the node rejects plaintext POSTs to `/v1/chat/completions` and `/v1/responses` unconditionally.
- **Operator responses must be sealed.** In `buildNonStreamResponder` and `buildFrameFactory`, a 2xx upstream response without `X-Zs-Response-Key` is a protocol violation (502 `operator_unsealed_response`, or failed stream setup). Pre-envelope errors (status >= 400 + `application/json`) still pass through so the caller sees the cause (`ticket_required`, etc.).
- **SSE pump**: `bufio.Reader.ReadBytes('\n')`, never `bufio.Scanner` (64KB line cap). `http.Client.Timeout` stays `0`; per-request cancellation comes from the request context.
- **The mid-stream failure path emits `data: {"error": …}` then `data: [DONE]`.** The error frame is plaintext even when the rest of the stream is encrypted (§5.3). Don't wrap `[DONE]`.
- **An over-large caller `max_output_tokens` is lowered, not refused.** `Client.dispatch` runs `inject.ClampMaxOutput` on the body — after the model is known, before `estimateTokens` — against `s.poolMaxOutput`, the LARGEST `max_output_tokens` declared by the operators this request could actually be routed to. `max_tokens` is an upper bound on generation, not a demand, so treating it as an eligibility predicate makes a client with a generous model card unroutable and reports `context_length_exceeded` on a request with abundant context headroom. Four properties are load-bearing:
  - It runs **pre-seal**, so the escrow and the body the node forwards upstream carry the same number (clamping only the escrow leaves the provider asked for the original).
  - It **only lowers** and never adds an omitted field, which would defeat the strictly better per-operator derive mode.
  - It is **skipped entirely when any serving operator declares no ceiling**, because undeclared means unbounded (`Fits`'s rollout gate) and that operator can honor the caller's value.
  - Because of that skip rule, the ceiling **must** be computed over the ROUTABLE set, not the raw registry — `registryProvider.Operators` filters on `ServesModel` alone, so one staging node (or a banned node, or one the caller's `provider` prefs exclude) declaring `0` would switch the clamp off for every payer on that model. `routableIgnoringSize` applies exactly the size-independent hard excludes; leaving one out only raises the ceiling (clamps less, degrades to the old behavior), while adding one selection would *not* apply clamps a caller below what an operator would have served — so only add predicates selection applies unconditionally.

  The **context window stays a hard filter** — `context_length_exceeded` after the clamp is always a genuine size miss: of the window for a pre-9.11 operator, of `CeilingForwardFactor` × its input ceiling for one that defers fit to its upstream. When the clamp fires the response carries `X-Zs-Max-Output-Clamped`; `Client.dispatch` reports the clamp through the emitter (`httpEmitter.clamped` in `go/zs/handler/emit.go`), which sets it on `w` before the node answers. That is why `httpEmitter.reply` and `httpEmitter.passThrough` snapshot the SDK's own `X-Zs-*` (`snapshotZsHeaders`) and re-assert them after the §5.2-step-4 strip (`stripNodeZsHeaders`). Restore, never an allow-list inside the strip: `copyResponseHeaders` runs first, so a node answering with the same header name has already overwritten the SDK's value and an exemption would forward the node's number as the SDK's.
- **`body_hash` mismatch on a receipt drives `OpenHandle.Protest`** with a dispute excerpt. That is **not** the path for happy-failure — zero-cost receipts are signed normally and acked via `AckSettle`.
- **`/v1/completions` is emulated, not native.** `handleCompletions` (`go/zs/handler/completions.go`) translates the legacy text-completion `prompt` → `messages`, dispatches it as an ordinary `/v1/chat/completions` so the node/relay/wire never learn it began as a completions call, then reshapes the chat response back to `text_completion` shape at the emitter's two write seams (`httpEmitter.reply` / `httpEmitter.frame`). The signal is the handler's `clientFormat`, which `Server.dispatch` hands to the emitter and the Client never sees; `formatChat` (the zero value) means no translation. Keep the reshape **after** receipt / `body_hash` verification — those run on the node's original chat bytes, so never reshape `contentFrames`. `/v1/embeddings` stays commented out in `routes()`: there's no chat equivalent to emulate it with, so leave it disabled unless explicitly asked.

## Privacy and logging

- **Default `store: false`, and never log content.** `Client.dispatch` runs three pre-seal mutators on the caller's body (`payer_mutator_vectors.json` pins them against the TS twin):
  - `inject.DefaultStoreFalse` sets `store: false` **only when the caller omitted it**; an explicit caller value (true or false) is preserved per SPEC.md "Upstream retention: caller-controlled, default off". Don't restore the unconditional overwrite — it would break Responses API `previous_response_id` continuation for callers that opted into `store: true`.
  - `inject.DropEmptyTools` strips an empty `tools: []` (and a dangling `tool_choice`) so a strict upstream (vLLM/SGLang pydantic) doesn't 422 a plain chat turn. JetBrains/Koog sends `tools: []`.
  - `inject.DropRoutingPreferences` strips the caller's top-level `provider` routing object, parsed just before via `selection.ExtractRoutingPreferences` into the `routingPrefs` threaded to `pickCandidates`. It's a payer-side operator-selection hint and must never reach the node or upstream.

  Never put request bodies, response bodies, deltas, prompts, completions, or tool-call arguments / outputs into `slog`, traces, or any persistent sink. Token counts, ticket / operator IDs, addresses, model names, latency, and microUSDC charges are fine.
- **One deliberate carve-out: operator/upstream *error envelopes* ARE logged** (default-on WARN, `responseErrorMessage` → "operator returned error" / "operator returned stream error" / "operator returned pre-envelope error"). An `{"error": …}` payload is control-plane, not prompt or completion content, and the SDK runs inside the payer's own process — obscuring "your request was rejected because X" from the owner is all cost, no benefit. The **node's** content+error non-retention guarantee is unchanged, because the node is multi-tenant. Don't widen the carve-out to non-error response bodies; full request/response dumps stay behind the host's debug-bodies switch (`go/zs/debug.go`).

## Routing, retry, and relay attribution

- **Sizing fit** goes through `selection.FitsContextWindowFor` (over `inject.FitsContextWindow`), in the shared filter and both SDKs' reserve leg alike. Don't reimplement the check. Payer and node deliberately differ by one term: a 9.11 node forwards up to `CeilingForwardFactor` × its input ceiling × (1 + its tolerance), and the payer leaves the tolerance out because it cannot see the operator's setting.
- **Affinity caches**: two `IDAffinity` LRUs (`go/zs/affinity.go` ↔ `sdk/src/affinity.ts`), each mapping an id to the exact `(operatorID, nodeID)` — continuation state lives in one node's upstream account, not merely its operator's.
  - `s.affinity` keys on chat `tool_call_id` and on the `call_id` of any Responses `input[]` / `output[]` item, and honors `affinity_policy` (`prefer` / `strict` / `none`). On Responses the pin is also what keeps a stateless (`store: false`) client's replayed reasoning on the upstream account that encrypted it; another account refuses the `encrypted_content`.
  - `s.responseAffinity` keys on `previous_response_id` for `/v1/responses` and is **strict regardless of `affinity_policy`** — the pin is a correctness invariant, since the upstream session lives in a specific node's account and falling through guarantees a 404. A cache miss on `previous_response_id` blocks with a 400 rather than guessing.

  Both caches are in-memory; don't add persistence without checking with the user. Reservation 429s normally fall through to the next operator, **except** under `affinity_policy: strict`, where the pinned operator is the only legal target — preserve that distinction if you touch the reservation loop.

- **Infrastructure 5xx is retried; a coded refusal never is** (`go/zs/transient_retry.go` ↔ `sdk/src/reserve-retry.ts`). No zs component emits 504, and a relaying node answers a failed forward with 502 `relay_upstream_unreachable` while every other relay code is 400/404/502/503 — so a 502/503/504/52x carrying **no** OpenAI-shaped `error.code` came from an operator's CDN / ingress / LB, typically mid-restart. `ReserveHTTPError` carries the raw `(status, code, Retry-After)` so `classifyReserveErr` hands off to the shared golden-vectored `go/transient`. **Don't** pattern-match a formatted error string, and **don't** widen the retry to coded errors — a `SizeError` / `BusyError` / `PayerRefusalError` / `provider_unavailable` is an answer, so re-asking produces it again and only delays the real error.
  - Shape: `reserveWithTransientRetry` does 3 attempts per candidate, **rotating the relay each time** (`CandidatesExcluding` + `SelectRelayHopWeighted`, the same primitives as `probeDetailsWithRetry`); then `Client.dispatch` re-sweeps the whole candidate list up to `transient.Sweeps` (4) times within `Config.RetryBudget` (default `transient.OverallDeadline`, 60s; TS `Config.retryBudget`).
  - Three invariants: the sweep guard requires `sweepTransient && !sweepRefused` **and** no accumulator set, so any considered refusal ends it; the sweep can only run **pre-payment**, which is what makes it safe by construction; and rotation never falls back to a direct send under privacy mode.
  - `reserveWithTransientRetry` returns the FINAL `op`/`hop` — the caller **must** adopt both (`op, hop = attempt.Op, attempt.Hop`). Why, on the `reserveAttempt` godoc.

- **Relay reputation is a soft downrank, not the target's `Operator.Reachable` bool.** In transport-privacy mode the per-relay forward-failure streak lives in `ChainOperatorSource` (`go/zs/relay_reputation.go`, `RelayReputation` iface, threshold 3, a single success resets, and evidence-neutral decay of one accrued unit per 10-minute cooldown — **decay, not reset**, so a chronically bad relay re-crosses the threshold on its next single failure while a recovered one walks all the way back) and is **distinct from** the operator's own target-probe health. That distinction is the whole point: a non-compliant 3.0 fork answers its own `/v1/zs/details` probe (`Operator.Reachable=true`) but drops forwards. `relayHopFor` and the discovery `selAll` build consult `RelayDownranked` to demote a bad relay to the **fallback tier**, never hard-excluding it, so cold-start fallback holds. The discovery builder expresses that tiering by setting `Reachable=false` only on its temporary `selection.Operator` projection; it does not mutate `Operator.Reachable` or target eligibility. Don't fold relay reputation into the stored operator's target-health bool, and don't make the downrank a hard exclusion.
  - **Attribution runs through the shared verdict** — `transient.Classify` then `transient.NarrowRelayed` over the route evidence — in `attributeRelayHop` (Go `dispatch.go`, called from `forward.go` / `sse.go` ↔ `sdk/src/sealed.ts`), so both SDKs charge the same hop for the same outcome. A transport error reaching the relay, a `protorelay.IsHopErrorCode` hop error, or (since 9.1) an unmarked front-door status from a relay advertising `wire.RelayHopHeaderMinVersion` all land on `AttrRelay` and record the **relay** down; a forwarded target response (sealed, or a target's own error, i.e. a recognized code) credits the relay.
  - **That is the ONE entry point, and a transport failure goes through it too** — `forward.go` and `sse.go` pass `transient.TransportFailureStatus` with a nil header and body, they do NOT reach past it to `recordRelayOutcome`. Hand-rolling "transport error ⇒ relay fault" against the store at those seams reaches neither `Classify` nor `NarrowRelayed`, and so cannot see a caller abort. Two things must stay: `attributeRelayHop` returns before the credit on `TransportFailureStatus` (nothing arrived to credit — structural, because `Classify` answering `AttrNone` on a coded body would otherwise walk straight into it), and the seam passes **the context the request actually rode** (`sse.go` passes its `upstreamCtx`, not the payer's `ctx`).
  - **`CallerAborted` is `ctx.Err() != nil`, and it is the inference leg's, not just the reserve leg's.** A payer hanging up surfaces as the same `TransportFailureStatus` as a dial failure to a dead relay, and `forwardRawNonStream` rides `r.Context()` while `Do` blocks for the whole generation — so without it a hang-up benches a healthy relay for a socket the SDK tore down itself. Deliberately **narrower** than `transient_retry.go::callerAborted`, which also counts any `net.Error` timeout: that leg's client has a 5s `DefaultReserveTimeout`, while the forward client sets `Client.Timeout` 0, so its timeouts are dial / TLS / `httpx.ForwardHeaderBackstop` and the first two are the relay's own fault. The TS predicate is `callerAborted: signal?.aborted` in `sdk/src/sealed.ts` — keep them in step. **Known residue:** the 5-minute header backstop firing while a relay sits byte-silent on a slow target (image/video generation) still charges the relay. Separating that from a dial timeout needs an `httptrace` `GotConn` hook on the forward hot path; not worth it until the strikes are observed.
  - **A residual `AttrUnknown` ATTRIBUTES nothing — and still must not credit.** After narrowing, that is a code-less status from a *pre-9.1* relay, or an **unmarked** gateway timeout (408/504/524, the set `NarrowRelayed` abstains on at every version). Keep the qualifier: a **marked** timeout is rule 5's business and lands on `AttrTarget`, correctly — the marker proves the relay ran its handler, so the timeout is its target's, and `TestAttributeRelayHop_MarkedCodelessTakesDifferential` pins exactly that with a 504. Crediting the residue is what lets a relay behind a broken CDN keep a spotless streak while dropping every forward, so don't add a credit here; the reserve loop's rotation differential is what establishes blame for the code-less part.
    - **The unmarked-timeout slice is remembered, on a THIRD streak** (`relayTimeoutStreak`, `RecordRelayForwardTimeout`, threshold **5** not 3, cooldown **60m** not 10m). Abstaining and forgetting are different things: a timeout that costs the relay nothing is how a CDN-fronted relay stays selected while killing forwards it can't answer in time. It **cannot** live on `relayFailStreak` — that streak is credited constantly by the shapes that still work (every reserve, every stream that got its headers), which erases the evidence before it crosses anything; same reason `relayStaleStreak` is separate. Four properties must hold: **penalty-only with the reachability differential** (uncorroborated ⇒ record *nothing*, never a credit — unlike `relay_upstream_unreachable`, the relay asserted nothing there is a claim about); **no success clears it**, only decay; the **higher threshold** compensates for acting on evidence the shared verdict refuses to attribute; and the **longer cooldown** is sized by how RARE the evidence is, not how stale — this streak has no probe feeder by construction (a details GET can't trip an idle timer), so at 10m it would oscillate at 1 forever and be inert. `go/transient` is deliberately **unchanged**: the evidence is stateful and vantage-specific, so it stays out of the per-response verdict. The status set (`steering.IsForwardTimeoutStatus`), all three streaks' thresholds and cooldowns, and the decay arithmetic live in `go/steering`, golden-vectored against `ts/src/steering`, and both SDKs' reputation stores (`relay_reputation.go` ↔ `sdk/src/routing/reputation.ts`) call it; a test pins the status set as disjoint from `transient.IsRelayFrontDoorStatus`.

      Two limits to know before sharpening this. **It is not buffered-only** — `sse.go` reaches `attributeRelayHop` on the non-SSE fallback, so a streaming request whose relay gave up before the target's headers arrived feeds it too. And **the corroboration is weaker than it reads**: `lastReachable` is the most recent probe outcome *across* cycles and `ProbeBudget` can skip nodes, so "we saw the target up" can be stale — and it is the only thing separating a wedged front door from a slow target. The threshold, the cooldown, and fallback-tier-not-exclusion bound that; don't turn it into a hard exclude.
  - The `wire.RelayHopHeader` rule has three gates that all fail closed and must stay that way: the version gate reads the relay's **advertised** version (`buildSelAll` seeds `wire.BootstrapProtoVersion()` — major with minor **0** — precisely so a never-probed peer can't be charged for a header nobody established it could set); a **marked** response is the relay's claim about the target rather than its own fault; and an **unmarked** 408/504/524 stays unattributed, because a relay is byte-silent while forwarding (unattributed, *not* unrecorded — see the timeout streak above, which is app-side and deliberately not part of this gate; a *marked* timeout is attributed to the target by the marker rule, not covered by this exclusion). The charge set is the explicit `transient.IsRelayFrontDoorStatus` allow-list — golden-vectored, so don't re-derive it as "retryable minus timeouts", and don't add the timeouts to it now that they're acted on elsewhere.
  - **One deliberate asymmetry**: the **discovery probe** (`go/zs/details.go` ↔ `sdk/src/details.ts`) applies that predicate **status-first, ignoring `error.code`**, because a front door emits its own coded JSON (Envoy `upstream_connect_error`, or a node's per-IP throttle answering a coded 429 ahead of `handleRelay`) and blaming the target for those evicted healthy nodes from `/v1/models`. The probe may do that because it only picks an error *type*; `NarrowRelayed` may not, because it would have to flip retryability.
  - `relay_upstream_unreachable` is the relay's *claim* that the target is down (not a hop error), handled **differentially** via `RecordRelayUpstreamUnreachable`: it counts against the relay only when the target was independently observed reachable this cycle (claim contradicted → the relay is dropping forwards while blaming the target); otherwise it credits the relay. That is what stops a non-compliant fork from black-holing every forward behind that code without ever accruing a streak. A **marked** code-less status takes `RecordRelayForwardedTargetFault` instead — the same differential minus the credit, since the relay asserted nothing beyond "my handler ran", so an uncorroborated claim records nothing rather than crediting (crediting would let every target restart wipe a half-broken relay's streak).
  - **The reserve hop is penalty-only, never a credit** — and a proven fault records via either a narrowed `AttrRelay` verdict or the **rotation differential**, which charges only the most recent held hop. The reasoning for all three rules is the file header and the success-branch comment in `go/zs/transient_retry.go`; don't restate it here.

- **Latency is a third, separate app-side signal — don't put it in the shared `selection` policy.** `go/zs/relay_latency.go` (`RelayLatency` iface on the same `ChainOperatorSource`) ↔ `sdk/src/routing/latency.ts` holds observed network-RTT EWMAs, keyed by `NodeRef` like reputation and reachability, in three keyings: pair `(relay,target)`, relay-endpoint, and target. It's recorded from the **discovery probe** (`probeDetailsWithRetry`) and the **reserve round-trip** (`Client.dispatch`, success only — latency is distinct from the reserve-hop reputation rule above, so recording it there does NOT violate "reserve hop unattributed"). It's deliberately **not** in `go/selection`, being stateful, per-process, and vantage-specific, so it isn't golden-vectorable. Every SDK host is a single payer, so the RTT vantage *is* the payer's.
  - **Relays** are picked by `relayHopFor` via latency-**weighted** rotation (`SelectRelayHopWeighted`, built on the behavior-preserving `selection.EligibleRelays`) — biased toward fast relays, with a `latencyFloorFraction` uniform floor that bounds concentration so SPEC §3f diffusion holds. It is the SDK's **only** relay picker: nothing calls `selection.SelectRelay` directly anymore, though the code comments still describe tiering in its terms, and it is that tiering `SelectRelayHopWeighted` preserves — which is why a downranked relay lands in the fallback tier rather than being excluded.
  - **Targets** are picked by `pickCandidates` via `bandByResponsiveness`, ordering on **combined expected response time = network RTT + on-chain TTFT + decode term**: `Operator.Metrics.LatencyEwmaMs` (co-signed TTFT, first token) plus a `decodeNormTokens/TokensPerSecEwma·1000` term (co-signed tokens/sec, the rest of the response), bucketed into ~500ms bands with price preserved *within* each band. The affinity pin stays first.
  - **Every term is shrunk toward the candidate-set median by a confidence** (`shrinkToMedian`). The shrink target is the median rather than zero because on an additive lower-is-faster score a term you leave out contributes 0 — it reads as *infinitely fast*, which is an exploit on any self-reported term and a free pass for any unmeasured peer. RTT is confidence 1 or 0; both **on-chain terms are discounted by `catalogConfidence` (1/sqrt(catalog size))**, because the chain holds one TTFT and one tok/s per *node*, folded on every settlement regardless of model — `settle()` carries no model argument, deliberately — so a broad-catalog node's aggregate is a mean over its whole mix while a specialist's is that model's real figure. Breadth is an *upper bound on possible dilution*, not an estimate of it (traffic is unobservable): deliberately pessimistic, and not to be "improved" into a traffic estimate. Breadth counts **token-output models only** (`producesTokens`; undeclared modalities count, image-only ones don't) — the contract folds both aggregates behind an `outputUsageType === USAGE_TOKENS` guard, so an image-only model has never written to the number being discounted. The median is **confidence-weighted** (`confidenceWeightedMedian`) and must stay so: a candidate sitting exactly on the median is unmoved by the shrink at any confidence, so a plain one-vote-each median would let a *majority* of diluted nodes define the reference point and keep its flattering numbers in full. It reduces to the plain median at equal confidences. Bands are then clamped to `maxBandsFromMedian` either side, bounding total displacement. The real fix is a locally-observed per-`(node, model)` sample; this discount is the stopgap.
  - The caller's `provider.sort` selects which terms enter the score (`responsivenessTerms(op, lat, mode)` — note `go/zs/registry_dynamic.go` has an unrelated `responsivenessScore`, which is probe priority, not routing): `latency` = RTT+TTFT only, `throughput` = decode term only, `price` = skip the reband entirely, absent = the full combined score. All are kept "lower = faster" so the banding stays uniform. tok/s is weighted lightly through `decodeNormTokens` because it is the noisiest term. Both on-chain terms are per-node **aggregates** across served models — hardware-speed proxies, not per-model figures (tok/s especially, since decode rate is model-size-dominated).

- **The weights demerit is peer evidence only, and it can only ever demote** (`go/zs/weights_trust.go`, applied in `pickCandidates` between the responsiveness banding and the backoff demotion; TS: the `contradicted` input to `sdk/src/routing/order.ts`, voted in `sdk/src/pick.ts`). Where ≥2 distinct operator **owners** advertise the same `weights_digest` for a model, a candidate advertising a different one is stable-partitioned to the tail. Four rules are load-bearing:
  - **Nothing self-reported may promote.** `weights_digest_trust` and `weights_registry_match` are node-authored strings, so preferring a node that claims `node_supervised` + `matched` hands the boldest liar the best placement. Only a *peer's* digest counts. That is also why the signal is demote-only: an operator gains nothing by publishing, so there is no placement to farm with a false claim.
  - **Owners, not nodes** — one owner's five nodes echo one config, and counting them five times lets a single operator manufacture a majority against an honest peer for the price of node registrations. A **tie** for the plurality is undecided, and **silence is free** (no digest is the honest state of every hosted passthrough).
  - **The vote spans the whole registry, not the eligible slice** — a peer held out by price ceiling, staging, or the caller's `provider` prefs still says something true about which bytes the model is. That is this **routing** vote, fed from `registryProvider.Operators(ctx, model)`, which is deliberately unfiltered. Don't carry the rule across to the **display** consensus `AllModelDetails` folds onto `/v1/zs/details` (or `deriveWeightsConsensus` in `sdk/src/catalog`): that aggregate describes what the payer will route to, so it is filtered along with the rest of the discovery surface, and the two votes are scoped differently on purpose.
  - **Demote, never drop.** The hard exclusion (`NodeExcluder`) is reserved for a node contradicting its own *signature*; a weights claim carries none. A legitimate local requant contradicts honestly, and a model one node serves must stay routable. A contradicted candidate is **reported even when the list is too short to reorder**, but the WARN is deduped to one line per `(model, node)` for the process lifetime (`Client.weightsWarned`), because the demerit recomputes on every `pickCandidates`.
  - **No pin exemption, and the `nil` at the call site is the decision.** `demoteContradictedWeights` reserves that parameter for a genuine *session continuation*, and neither Go pin is one here: the `previous_response_id` pin has already returned a single-operator list and never reaches the post-passes, and the tool-call pin (`preferredOp`) is collapsed to one candidate by `SelectTargets` under `strict` — so the exemption could only fire under `prefer`, where the pin is a KV-cache preference. Exempting a preference makes the demerit inert for a payer bound to the contradicted operator across a whole tool loop (affinity TTL, 10m), which is exactly who is paying for a substituted model. The TS twin has no exemption at all (`order.ts`: "No pin is exempt").

  Honest ceiling: copying the real digest off the model's HF page is free and defeats a registry cross-check by construction. What it doesn't defeat is the operator's own runtime (the node's `reconcileWithRuntime`). The vote is `steering.WeightsConsensus`, golden-vectored against `ts/src/steering`. The evidence itself can't be shared — it is the details envelopes *this process* probed — so two payers can disagree, which is why the vote is not part of `go/selection`.

- **A 429 is four conditions, and only one is re-askable** (`go/zs/reserve.go` `BusyError.Code` ↔ `sdk/src/reserve.ts`). The node emits `no_capacity` (ticket store momentarily full), `payer_slot_cap`, `rate_limited`, and `reserve_temporarily_banned` all as HTTP 429. Only `no_capacity` is time-varying, so it is the only one the busy re-sweep re-asks. The other three must never be re-asked, and an absent or unrecognized code **fails closed**:
  - `payer_slot_cap` calls the node's `penaltyBox.RecordSlotCapTrip` **per ask** (weight 2 against a 20-point budget, 1-minute doubling ban), so a retry loop turns transient over-subscription into a real ban.
  - `rate_limited` is a fixed-window token bucket; `reserve_temporarily_banned` outlasts any sane schedule.
  - **Caveat on `rate_limited`**: in transport-privacy mode a relay's own per-IP throttle answers 429 `rate_limited` before `handleRelay` ever runs (`node/internal/server/relay.go` documents this as a known gap). Rotating the hop WOULD change that answer, but the marker-absence evidence that would prove it is deliberately not read on the dispatch path (`NarrowRelayed` may not flip retryability), so a relay-throttled 429 is treated as non-re-askable — correct as a fail-closed default, but the busy re-sweep cannot route around a throttling relay.
  - **Which of the four is not derivable from `busyHint`**: a 429 with no `Retry-After` leaves that at zero, so "was anyone at capacity?" is a separate sticky `anyBusy` bool, and it is what the terminal ladder's `toolFactorMissing` / `ephemeralMissing` / `priceRejected` branches gate on. Getting that wrong reports `no_ephemeral_capacity` when the pool was merely full.
  - The re-sweep has its own small budget (`busyRetries` / `busyRetryBudget` ↔ `BUSY_RETRIES` / `BUSY_RETRY_BUDGET_MS` in `sdk/src/pacing.ts`, distinct from `transient.OverallDeadline` — waiting out a fleet restart is worth a minute, waiting for a queue slot is worth seconds) and a **narrower** disqualifier set than the weather sweep: only the outcomes that outrank busy may veto it: a hard refusal, a size rejection or a relay gap (`busyBlocked := o.HardRefused || o.SizeRejected || o.RelayUnavailable` in `candidate_verdict.go` ↔ `routing/verdict.ts`, pinned by `dispatch_verdict_vectors.json`). `toolFactorMissing` / `ephemeralMissing` / `priceRejected` are gated on `!anyBusy` and are therefore subordinate to busy — letting them veto disables the re-sweep for whole requests, since a node trips `ephemeralMissing` routinely on a rotation gap.

    **The definition is `transient.RetryableBusyCode`** (`go/transient`, beside the four `BusyCode*` constants) ↔ `retryableBusyCode` (`ts/src/transient`), golden-vectored. `BusyError.Retryable()` and the TS `BusyError.retryable` both delegate to it; don't re-inline the comparison. **Both fail closed**, so a fifth node code is never re-asked, which costs a round trip rather than money. The mistake that does cost money is gating on the bare 429 status: that re-asks all four codes and spends a `payer_slot_cap` strike on every ask. Neither SDK records a target strike for any 429, since a node at capacity answers its details probe normally the whole time.

## Settlement

- **The settlement rules live in `settle.Classify`, and each rail maps its ticket onto them.** `settle.Classify(view, now) → Wait|Refund|Lapse|Arbitrate|Unknown` is the one answer to "what call does the contract allow on this ticket right now", over a rail-neutral `settle.Ticket` (status and deadline); `escrow.Classify(box, now)` is the Algorand entry point, mapping the box through `(*TicketRecord).View()`. It is shared by the refund watchdog, `zs-proxy tickets`, and the node's sweep (TS: `classify` in `ts/src/settle`, with `ticketView` / `classify` in `ts/src/escrow/classify.ts`; pinned by `settle_vectors.json` and, for the box mapping, `escrow_vectors.json`). The reconciler's `decideSettlement` sits on top of it in both SDKs, and `decideTicket` is its Algorand wrapper. Don't re-derive a status/deadline table locally — that drift is what made the watchdog retry `refundInactive` against operator-pending tickets it could never refund. **FROZEN is terminal** (no method accepts a frozen ticket, so its USDC *and* its MBR slot lock forever), and **`Unknown` ≠ `Wait`** (an unrecognized status usually means bindings older than the deployed contract; never render it as "too early"). Ticket boxes are fetched via `escrow.FetchAllTickets` — never hand-roll a box walk. It reports `Unreadable` boxes rather than failing, since one undecodable box must not hide the rest. Such a box can't be attributed to a payer either, because the address is inside the value that failed to parse (`zs-proxy tickets` reports these separately).
- **A failed settle ack is never followed by a broadcast** (SPEC §3a "Settle ack"). A refusal is the node's answer about its own group, and a transport failure may have delivered it, so either way the ticket finishes on the operator's driver path. The one exception is `errNoSettleAckRoute` ↔ `NoSettleAckRouteError`: no ≥ 9.12 relay to carry the ack, decided before anything is sent, which falls back to the payer's own broadcast rather than a direct send from the payer's IP.
- **One `zs-receipt` frame per stream** (`receiptSeen` in the frame factory, `zs/dispatch.go` ↔ `sdk/src/stream.ts`). A host's spend accounting depends on it: with two frames an operator could take both branches, a bad-signature receipt that releases the reservation and then a valid one whose settle finds nothing open, hiding the charge from the payer's cap (`proxy/` `internal/spend`).
- **`tokenize.SafeEstimator` returns a deliberate upper bound** (a versioned bound, selected by `InputTokenBoundVersion`, plus image tile tokens and a flat margin; see `zs/tokenize/safe.go`). Don't make it byte-exact — settlement reconciles to actual usage via the operator's signed receipt, so overestimates only widen the refund.

## Releasing and pushing

Full procedure: README "Releasing". The rules that bite:
- Go, `@txnlab/zs-proto` and `@txnlab/zerosignal` release in **lockstep** — one version, three tags (`go/vX.Y.Z`, `ts/vX.Y.Z`, `sdk/vX.Y.Z`) on one commit. `make release-pr VERSION=X.Y.Z` makes the version commit and its PR; after the merge, `make release-tag` reads the version from `main`'s `package.json` files, tags the commit that set it with all three, and pushes exactly those three. The Go tag is requested **without** its prefix: `go get github.com/TxnLab/zerosignal/go@vX.Y.Z`. Never move or delete a pushed `go/v*` tag.
- npm releases are **staged** by CI and go live only on a maintainer's 2FA approval. The repo and its releases are private: both packages publish `--access restricted`, and the Go module needs `GOPRIVATE=github.com/TxnLab/*`.
- Commits pushed here must use the GitHub **noreply** address — a push carrying a private email is rejected (GH007).
- No `hayai` naming in new code (`make check-no-hayai`).
